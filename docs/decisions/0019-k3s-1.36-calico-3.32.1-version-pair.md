# ADR-0019: Pin k3s v1.36.x + Calico v3.32.1 as a matched pair; pre-apply the #12890 LoadBalancer-IPAM RBAC workaround

- **Date:** 2026-08-02 (decided) · 2026-08-03 (applied, from-scratch rebuild) · 2026-08-16 (workaround verified necessary and working)
- **Status:** Accepted
- **Supersedes / related:** [ADR-0018](0018-calico-bgp-replaces-metallb.md) (needs ≥3.30 for LB IPAM), [ADR-0020](0020-crd-tier-vendored-server-side-apply.md) (the second 3.32 gotcha this bump surfaced), [ADR-0003](0003-k3s.md). Code: `ansible/inventory/group_vars/all/vars.yml` (`k3s_version_default`, `calico_version`), `gitops/infrastructure/calico/helmrelease.yaml`, `gitops/infrastructure/calico-bgp/kube-controllers-ipamconfigs-rbac.yaml`.

## Context

### k3s was on an EOL Kubernetes

We were running **k3s v1.32.3**. Upstream Kubernetes maintains release branches
for **the most recent three minors only** — at the time 1.36, 1.35, 1.34 — so
1.32 was two minors below the oldest supported. Not "would be nice to be newer";
an unsupported Kubernetes.

- **1.36 was current stable** (released 2026-04-22), not pre-release.
  **1.37 was due 2026-08-26**, three weeks out. Don't chase 1.37: Calico
  support for it won't land until ~3.33, and being ahead of your CNI is worse
  than being one behind. Landing on 1.36 means being a normal, supported N-1
  once 1.37 ships.
- **No provisioning gate.** The Flatcar sysext bakery publishes k3s transfer
  configs for v1.32 → v1.36 (verified via `gh api
  repos/flatcar/sysext-bakery/releases/tags/k3s`). The `.raw` images resolve at
  download time through the `MatchPattern` in `k3s-sysupdate.conf.j2`, so a
  minor bump is just `k3s_version` in `group_vars`.
- **The four-minor jump costs nothing here.** Kubernetes only supports
  one-minor-at-a-time for *in-place* upgrades, but this cluster was empty and
  from-scratch rebuild was already proven. So we re-provision at the target
  minor rather than walking 1.32→1.33→1.34→1.35→1.36. This is the payoff of the
  immutable provisioning; it evaporates the moment there's real state.

### Calico had to move for LoadBalancer IPAM

Our pinned **v3.29.1 cannot allocate LoadBalancer IPs — only advertise them.**
The 3.29 docs say so verbatim: "Service LoadBalancer address allocation is
outside the current scope of Calico, but can be implemented with an external
controller." Their recommended 3.29 setup keeps MetalLB's controller with the
speaker disabled. So "drop MetalLB entirely" ([ADR-0018](0018-calico-bgp-replaces-metallb.md))
was simply not reachable at that pin.

**LoadBalancer IPAM landed in OSS v3.30.** It needs an explicit `IPPool` with
`allowedUses: [LoadBalancer]` + `assignmentMode: Automatic`; the LB controller
is enabled by default in kube-controllers.

### The known bug in 3.32

[projectcalico/calico#12890](https://github.com/projectcalico/calico/issues/12890)
(filed 2026-06-02, open): LB IPs stuck `pending` while BGP advertises the
routes fine, because `calico-kube-controllers` can't read `ipamconfigs` (the
ClusterRole grants `ipamconfigurations`). The full thread was read on
2026-08-02, and the evidence is stronger than a single lab report:

- **Three independent parties, two distros.** The reporter on k3s 1.36.1 +
  Debian/Raspbian arm64 + Mikrotik ROS (four real nodes — *not* kind, despite
  how it may skim); a second reproduction on rke2 v1.35.5; a third confirming
  the fix. Neither kind-, arch-, nor k3s-specific.
- **The reporter bisected it.** Two days after filing: the same procedure on
  k3s 1.35.5 + Calico 3.31 assigned and routed LB IPs correctly. Same person,
  same hardware — **3.32 broken, 3.31 works.**
- **Root cause is one PR.** [#11839](https://github.com/projectcalico/calico/pull/11839),
  *"Fix ipamconfigs -> ipamconfigurations"*, milestone v3.32.0, renamed the
  ClusterRole grant to `ipamconfigurations` while the deployed CRD is still
  `ipamconfigs`. A half-finished CRD migration, not a flake — and it explains
  why 3.31 works: the rename isn't in 3.31.
- **A confirmed workaround exists** (an extra ClusterRole granting
  `ipamconfigs` to the `calico-kube-controllers` SA in `calico-system`),
  posted by the second reporter and confirmed by the third.
- **What's genuinely weak:** the reporter self-describes as unsure of the root
  cause; their paste has an internal inconsistency (a `jsonpath` showing SA
  `calico-kube-controller`, singular); their repro pre-installs the v1 CRD
  bundle by hand and uses raw manifests rather than the Helm chart, so our
  install path is not identical. The working RBAC fix makes the diagnosis solid
  regardless.
- **Zero maintainer engagement after two months.** All three commenters
  unaffiliated, no labels, no linked PR. Treat as unfixed and unattended.
- **⚠ `v3.32.1` does NOT contain a fix.** Confirmed: the only RBAC change on
  `release-v3.32` since the report is an unrelated kubevirt grant (#12996). The
  workaround is **required**, not precautionary.

## Decision

**k3s `v1.36.x` + Calico `v3.32.1`, and the #12890 RBAC workaround is
pre-applied — with the Calico prime, not reactively.**

Candidate pairings at decision time:

| k3s | Calico | Verdict |
|---|---|---|
| **1.36** | **3.32.1** | **✅ Chosen.** Matched pair, both latest stable; #12890 pre-empted by the workaround. |
| 1.36 | 3.31 | Would need 3.31↔1.36 support confirmed; moot now. |
| 1.35 | 3.31 | Attested working in #12890's thread; the conservative option we passed on. |

Why latest-with-a-known-bug rather than the safe line (an earlier draft
recommended 3.31.x; that is superseded):

- **The bug is fully understood, not a mystery** — one PR explains the whole
  thing.
- **The failure is loud, immediate, and pre-empted.** With the workaround
  applied up front we never hit it; if it somehow fires, the signature is
  unmistakable (LB IPs `pending`, one specific `ipam.go` log line).
- **3.32 corresponds with Kubernetes 1.36**, so the pairing objection that
  drove the earlier 3.31 recommendation is gone, and it's one rebuild instead
  of two.
- Release landscape: v3.32.1 (2026-06-26) was the latest *stable* —
  `releases/latest` returns it, excluding prereleases by definition;
  `v3.33.0-0.dev` existed but no v3.33.0 and no RC.

The workaround, in `gitops/infrastructure/calico-bgp/kube-controllers-ipamconfigs-rbac.yaml`:

```yaml
# WORKAROUND for projectcalico/calico#12890 — REMOVE when fixed.
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: calico-kube-controllers-ipamconfigs-workaround
rules:
  - apiGroups: [projectcalico.org, crd.projectcalico.org]
    resources: [ipamconfigs]
    verbs: [get, list, create, update, delete, watch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: calico-kube-controllers-ipamconfigs-workaround
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: calico-kube-controllers-ipamconfigs-workaround
subjects:
  - kind: ServiceAccount
    name: calico-kube-controllers
    namespace: calico-system
```

Both API groups are granted — the error is on `crd.projectcalico.org`, but the
confirmed-working version grants both. **The verb list is broader than the
observed failure requires** (the log only shows a failed `get`); it is kept as
posted because that is the *confirmed-working* set, and inventing a narrower
untested variant during a CNI migration is the wrong time to economise.
Tighten to `get,list,watch` later as its own change.

**The versions deliberately did NOT land with the encapsulation change**,
contrary to the original "one rebuild instead of two" plan: the BGP work was
blocked on pfSense values while the version bump had no external dependency,
so batching would have held a ready change hostage *and* put two variables in
one rebuild.

**`calico_version` is deliberately fleet-wide, not per-cluster** (unlike
`k3s_version`, [ADR-0026](0026-per-cluster-derivation-from-index.md)). k3s's
version reaches a node through Ignition alone, so per-cluster costs nothing;
`calico_version` is dual-owned with `gitops/` (the HelmRelease chart version
must match for clean adoption, and `crds.yaml` is per-version), so per-cluster
Calico forces a per-cluster gitops layout. Do that when a second cluster
exists, not before.

## Alternatives rejected

- **Stay on 1.32 / 3.29.1** — unsupported Kubernetes, and LB IPAM is
  unavailable at that Calico line.
- **Calico 3.31.x** (the earlier recommendation) — works around #12890 by
  avoiding it, but is not the version-matched pair for 1.36, and would need
  another bump soon.
- **Sequential in-place minor upgrades** — pointless on a disposable cluster;
  re-provision at the target.
- **Wait for 1.37 / 3.33** — being ahead of the CNI is worse than one behind.
- **Apply the workaround reactively, when LB IPs stick** — rejected: LB
  allocation gates the Gateway → cert-manager → ESO chain, so a gap stalls the
  bootstrap, and the BGP side gives no hint. Priming it alongside Calico closes
  the gap and is idempotent.

## Consequences

- **Repo-wide guardrails** (root `CLAUDE.md`): keep k3s on a supported minor;
  bump via `k3s_version` + re-provision, never sequential in-place while the
  cluster is disposable; Calico 3.32 needs the workaround, non-optional.
- **🔁 Removal criteria — re-check on every Calico bump.** This is deliberate
  cruft with an expiry. Drop it once either (a) the shipped
  `calico-kube-controllers` ClusterRole grants `ipamconfigs`, or (b) the CRD is
  actually renamed to `ipamconfigurations` so upstream's grant matches. Check
  *after removing*:
  ```
  kubectl auth can-i get ipamconfigs \
    --as=system:serviceaccount:calico-system:calico-kube-controllers
  ```
  If it still says `yes`, upstream fixed it and the workaround can go. While
  the workaround is in place, `bootstrap-cluster.yml` asserts this returns
  `yes` — a `no` means LB IPs will sit `pending` while BGP looks healthy.
  Renovate may track the 3.32 line, but every bump must re-run this check.
- **We walked through a one-way gate:** v3.32 requires migrating to
  **ClusterNetworkPolicy** (Admin/Baseline Admin Network Policies are replaced).
  Verified a no-op for us — no policies existed. Future pod-isolation work
  uses Calico `GlobalNetworkPolicy`/`ClusterNetworkPolicy`, never the
  deprecated AdminNetworkPolicy path.
- **Second, unrelated 3.32 gotcha, hit on the first bootstrap at the new pin:**
  v3.32 removed the CRDs from the tigera-operator chart. Resolved by
  [ADR-0020](0020-crd-tier-vendored-server-side-apply.md); on every
  `calico_version` bump, regenerate `crds.yaml` in the same commit as
  `vars.yml` + `helmrelease.yaml`.
- Bumping `k3s_minor` re-points sysupdate at the new minor's transfer config:
  the seeded and running versions re-converge at rebuild, then drift again
  within the new minor — expected, not drift.
- **Contingency** if LB IPAM misbehaves for some *other* reason: MetalLB's
  controller only (speaker disabled), per Calico's own 3.29 docs. The dataplane
  decision stands regardless.
- Worth a look before touching anything: [projectcalico#9457](https://github.com/projectcalico/calico/issues/9457),
  "VXLanCrossSubnet issue on v3.29" — our previous version *and* mode. Title
  only; not yet read.

## Evidence

Applied 2026-08-03 on a from-scratch rebuild (k3s `v1.36.2+k3s1`, Calico
`v3.32.1`). On 2026-08-16 the `can-i` assert returned `yes` and a test Service
was allocated an LB IP with no `pending` phase — the workaround works and was
necessary. (This does not prove upstream is still broken; that check is the
removal criterion.) See [`../worklog.md`](../worklog.md).
